The Compiler

Description

RCC16 is an Oric targeted version of the LCC Compiler.

This compiler is decently ANSI compliant, and event support C++ comments as well as standard C comments.

The "official" source repository whre all the changes for the compiler are made before they reach the OSDK is Fabrice Frances' GitHub

Here is the primary source for the C Cross-Compiler targetting the 6502 processor that is included in the OSDK (Oric Software Development Kit). I am (Fabrice) putting it here so that it eventually becomes more familiar to people willing to maintain it in the long term...

Also, in order to increase its maintenability, I will try to progressively document what my 6502 code generator does. If you are interested in it, the first thing to read is Hanson & Fraser's interfacing document (docs/INTERFAC.pdf): the lcc65 compiler is built from Hanson & Fraser's frontend, and my small 6502 backend (6502/src/gen.c).

The frontend supplies the backend with forest of dags (directed acyclic graphs), the backend is responsible for code generation. The following options are accepted by the backend and affect the generated output; comparison of these outputs give a better understanding of what the backend does...

  • -G generates a graph output (in Graphviz dot format) instead of code output. The output is a representation of the forests of dags produced by the frontend, which means that the backend doesn't do any work (except transformation of Hanson & Fraser's internal structures to Graphviz dot format). For example, the visual representation of the compilation of tests/torture_test.c file gives the graph (tests/torture_test.dot), which once converted to pdf ("dot -Tpdf torture_test.dot") can be graphically seen in tests/torture_test.pdf.

  • -O0 transforms the graph into code. More precisely, for each function, the backend first linearizes the forest of dags given by the frontend, allocates temporary variables to hold the result of operators, defines a number of "operand handling modes" (Constants, Direct, ZeroPage, Indirect, Y-Indexed) that will be used for optimizing the code in the advanced -O2 and -O3 optimizations, and generates 16-bit macro-instructions instead of 6502 opcodes in order to keep the generator small.

  • -O1 removes the leaf nodes of the graph (ADDRG, ADDRF, ADDRL, CNST) so that their value become direct operands of the nodes above them. At the same time, this removes the need for the associated temporary variables.

  • -O2 allocates some parameters and some local variables into "virtual-registers" in zero-page: these zero-page variables are of course faster than the normal parameters or local variables which are accessed on a software stack (i.e using indirect Y-indexed access). -O2 also does some simple optimizations like converting additions/substractions with 1 to INC/DEC operations, special treatment of 1-bit shifts or equality with 0, removal of some un-necessary conversions between chars/ints/unsigned ints, removal of function prologue/epilogue when possible.

  • -O3 goes further and removes indirection nodes (ASGN, INDIR) from the usual code patterns, so that the addressing mode of the 16-bit macros absorbs the extra indirection. This used to be described as an attempt, and with good reason: three of its folds were unsound and could silently generate wrong code, which is where the old "my program only works at -O2" reports came from. Those were tracked down and fixed in OSDK 2.0, so -O3 is now dependable, and the per-function pragma below exists for the rare case where you want to hold one function at a lower level anyway.

Last but not least, the sources of the lcc frontend are very old (they come from LCC 1.9) and are written in K&R style, so compiling them still produces a healthy pile of warnings. They do build cleanly on Windows though: the compiler is part of the osdk-vsnet.sln Visual Studio solution along with the rest of the toolchain, and that is how the shipped binaries are produced. The Code::Blocks projects are still present, and Linux users have a Makefile per tool, which matters because the compiler is expected to stay buildable there.

The optimisation level is set with the OSDKCOMP variable. When it is not defined, the build uses -O2. Besides -O0 to -O3 there is also -Os, which optimises for size rather than speed.

Which options should I use?

The defaults are deliberately middle of the road, and the right settings depend on what you are doing. None of this is obvious from the option list, so here are the three cases that actually come up.

A release build: smallest and fastest.

SET OSDKCOMP=-O3
SET OSDKMACRO=-O

-O3 is the most aggressive code generation, and OSDKMACRO=-O runs the 6502 peephole optimizer over the expanded output. These are two separate switches and both matter: the peephole is worth up to 20% on its own on char heavy code, so "-O3" without it is leaving a lot behind. Leave OSDKDEBUG unset, which is the default. If you need size rather than speed, use -Os in place of -O3.

Debugging C code in the VS Code extension.

SET OSDKCOMP=-O2
SET OSDKMACRO=-O
SET OSDKDEBUG=-g1

-g1 makes the compiler emit the source line and type information the debugger needs to show you C lines and typed variables instead of disassembly. It is not the default because it is not free: it also keeps local variables that would otherwise be optimised away, so that they still exist to be inspected. On a normal program that is a handful of bytes, in the functions that have such a variable.

Note that -g1 alone does not make every local visible. At -O2 and above the compiler promotes frequently used locals into zero page registers and can drop the stack frame entirely, and no amount of debug information brings those back. To inspect a specific function properly, wrap it in the pragma described in the next chapter while leaving the rest of the project optimised.

Chasing a code generation bug.

SET OSDKCOMP=-O1
SET OSDKMACRO=

If a program misbehaves and you suspect the toolchain rather than your own code, drop to -O1 and turn the peephole off. If the problem disappears, re-enable them one at a time: that tells you whether it is the code generator or the peephole, which is the first thing anyone will ask.

One caveat when comparing numbers with someone else: OSDKCOMP and OSDKMACRO are independent, so "built at -O3" is ambiguous unless the peephole setting is stated too.

Changing the optimization level per function

Since version 2.0, the optimization level can also be changed from the source code itself, overriding the -On command line option for the function definitions that follow:

  • #pragma optimize(push, n) saves the current level and switches to level n (0 to 3)
  • #pragma optimize(pop) restores the previously saved level
  • #pragma optimize(n) switches to level n without saving the current one

The main use case is debugging: at -O2 and above the compiler promotes frequently used parameters and local variables to zero page virtual registers, and can omit the stack frame entirely, which makes the locals of a function invisible to a source level debugger. Dropping the whole project to -O1 restores them, but the generated code may then become too large to fit in memory. Instead, only the functions being debugged can be wrapped in a pragma pair while the rest of the project stays fully optimized:

#pragma optimize(push, 1)   // locals stay on the stack frame, visible to the debugger
void function_being_debugged(void)
{
    ...
}
#pragma optimize(pop)       // back to the level given on the command line

The same mechanism works the other way around: selected functions known to compile correctly at the more aggressive -O3 level can be raised individually while the rest of the project keeps the safer -O2 default.

Some details worth knowing:

  • A pragma placed between two functions applies to the functions that follow it; a pragma placed inside a function body applies to that entire function (code is generated when the closing brace is reached)
  • push/pop pairs can be nested up to 16 levels deep; an unmatched pop or a malformed pragma produces a warning and is otherwise ignored
  • Older versions of the compiler silently ignore the pragma, so source code using it remains compilable

The mixed/debug_type_zoo sample shows the pragma in action: the project builds at -O2 while the two functions meant to be inspected in the debugger are compiled at -O1.

Calling convention

By default, arguments are passed on a software stack. A function can instead be declared __fastcall to receive its arguments in registers, which is significantly cheaper for small, frequently called functions. The register width comes from the prototype, so a char arrives in A, and a pointer or int in A:X. Most of the small library functions have been converted.

Data types

Since the 6502 is an 8 bit processor, the data size are as follow:

  • Pointers are 16 bits long
  • char and shorts are 8 bits long (note: standard C requires short to be at least 16 bits; here it is an alias of char)
  • int are 16 bits long
  • long and unsigned long are 32 bits (since OSDK 2.0; in earlier versions long was an alias of int and code relying on 32 bit arithmetic silently computed wrong results). 32 bit arithmetic is naturally slower and larger than 16 bit on a 6502 (multiply, divide and shifts go through runtime routines), so prefer int/unsigned where 16 bits suffice. Current limitations: long values are never allocated to register variables, converting between float and long only covers the 16 bit int range, and printf has no %ld support yet
  • float and double are the 40 bits (5 bytes) Oric ROM floating point format

Libraries

Some standard functions (memcpy, printf, ...) are implemented, but most of the standard library is not available.

Some functions are just quick hacks done by directly calling the ROM functions. Unfortunately, ROM releases are different, and thus any code calling these functions will work only on ATMOS.

Historic

Here is the list of all releases with a short description of things that changed:

Version 2.0

- Debug output is selected with the new OSDKDEBUG build variable rather than being folded into OSDKCOMP, so setting your own optimization flags cannot silently lose it. It is empty by default; set OSDKDEBUG=-g1 to debug at C level. See "Which options should I use?" above
- Fixed -O3 storing a call result through a stale pointer, and at the wrong width. For "dst[i] = f(...)" the assign-into-call fold stored through the destination address temporary, which the call had already clobbered, and it inherited the call's width, so an int returning function folded into a char assignment wrote a word over the neighbouring byte. This was the long standing "aes256 fails at -O3" report
- Fixed -O3 passing an address instead of a value for "f(*(arr+i))". Conversion elision compared operands by name only, so a folded indirection looked identical to the pointer itself; it now also requires the addressing modes to match
- Fixed -O3 releasing a shared temporary too early, which corrupted the pointer in expressions like "p->a==a && p->b==b && p->c==c". A folded indirection now only takes ownership of its child temporary when it consumed the last reference to it
- Fixed the macro library computing the wrong page for pointers whose low byte is $FF: because < and > bind the whole trailing expression, "#HIGH(cte)+1" actually meant "HIGH(cte+1)". Affected MOVW_CY and six shift macros
- Fixed ASGNW_YD always miscompiling the low byte: it discarded the byte it had just loaded and left Y wrong for the store
- The project include path given with -I is now searched before the bundled include folder, so a project can override a shipped header
- The INCLUDE and C_INCLUDE_PATH environment variables are cleared around the preprocessing pass. The new preprocessor honoured them, so building from a Visual Studio developer prompt silently pulled in MSVC system headers
- Functions can be declared __fastcall to receive their arguments in registers instead of on the software stack. The register width comes from the prototype, so a char arrives in A and a pointer or int in A:X. Most of the small, frequently called library functions have been converted
- long is now a real 32 bit type. It used to be 16 bits, so any program relying on 32 bit intermediates silently computed the wrong answer
- Native 8 bit arithmetic for char operands: + - & | ^ ~, comparisons and shifts stay in 8 bits instead of being promoted to 16, in place increments become inc/dec, and a byte comparison against zero drops the redundant cmp #0
- Small constant left shifts are unrolled, and a 16 bit shift by exactly 8 becomes a byte move rather than an 8 step loop
- New -Os flag to optimize for size, alongside the existing -O1/-O2/-O3
- Automatic locals that are only ever written and never read are eliminated, and when that empties the stack frame the frame setup goes with it
- Uninitialized statics are reserved in .bss instead of being written into the executable as a block of zeros. A "static int table[4096]" used to cost 8K of file size, and of load time, for nothing. Because a reservation in .bss is not filled, the runtime now clears the region at startup, and that clear is only emitted when a module actually reserves .bss
- Static local variable labels include the C name, which makes the generated assembly readable
- Fixed a regression that made any floating point expression fail with an "expression too complex" error
- Added support for 0b binary integer literals - Emits .csource line markers and .ctype type annotations when compiling with -g, so debuggers can map generated code back to the C source and display typed variables
- New #pragma optimize(push, n) / #pragma optimize(pop) / #pragma optimize(n) to change the optimization level per function

Version 1.40

- The compiler now reports a proper error when an expression is too complex and runs out of temporary registers (max 8), instead of silently emitting invalid assembly code

Version 1.39

- fix to allow inline assembler directives to be inserted at the proper location in the functions

Version 1.38

- integrated all the latest changes from Fabrice Frances: Fixes some issues found by Goyo and Retroric regarding encoding of data tables by the compiler

Version 1.36

- fixes for the -O0 output

Version 1.35

- defstring is used by the frontend not only to define strings (signed char data) but also for initializing unsigned char arrays. In this case, defstring will receive char data with possible negative char values which have to be printed as their corresponding unsigned char value.
